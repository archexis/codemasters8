## Основание и границы

План учитывает README, STACK_MIGRATION.md, старые REQUIREMENTS_MATRIX.md и IMPLEMENTATION_HANDOFF.md, текущие types/domain/scoring/analysis, тесты и CI. Старый аудит относится к версии до переноса. Отчёты о миграции и DeepSeek — исходные свидетельства, а не приёмка текущей рабочей копии. Во время подготовки плана тесты не запускались.

В рабочей копии уже есть Svelte/TypeScript, серверные команды, хранилище файлов и внешний AI. Сначала проверяем реализованное; повторно разрабатывать работающие функции не нужно. Рабочее дерево содержит многочисленные незакоммиченные изменения: перед реализацией фиксируем их состав и безопасную точку восстановления, не удаляем и не откатываем чужую работу.

MVP: объект → публикация → анализ → доказательство → решение аналитика → скоринг → сигнал → экспорт. DEMO и подключённый режим различимы. Автоматический сбор рекламы, OCR, CV, общие организации и сложная ролевая модель не входят в этот план. Мониторинг MVP — ручное внесение и CSV с происхождением данных. Их расширение требует отдельного scope.

Правовые инварианты ниже — правила продукта из имеющихся требований, а не заключение об актуальном законодательстве или конкретном застройщике.

## Обязательные правила перехода

1. Единственная последовательность: 0 → 1 → 2 → 3 → 4 → 5 → 6. Реализация следующего спринта начинается только после PASS предыдущего. Можно заранее выявлять зависимости, но нельзя засчитывать незавершённые работы как готовые.
2. Каждый критерий DoD имеет ID, проверку, ожидаемый результат и свидетельство. Статусы: NOT_RUN, PASS, FAIL, BLOCKED. Пропущенная проверка, отсутствие окружения, flaky-тест и UNVERIFIED не являются PASS.
3. DoD выполнен только целиком. Нет правила «почти готово» и переноса обязательного критерия в следующий спринт. Изменение scope оформляется явно до приёмки, не используется для сокрытия ошибки.
4. Для каждого спринта создаётся `docs/acceptance/sprint-N.md`: версия исходников (SHA и diff либо хеш снимка незакоммиченной работы), окружение, ID критериев, команды, результаты, артефакты, дефекты, дата и ответственный за проверку. Секреты и персональные данные в отчёт не включаются.
5. На выходе каждого спринта проходят `npm run check`, `npm test`, `npm run build` и затронутые интеграционные/E2E-проверки. Если менялся серверный контракт — также соответствующие API/Edge/DB проверки. Для документационных правок повторный полный прогон не нужен.
6. Все обязательные проверки спринта и накопленные проверки предыдущих спринтов зелёные. Нет открытых дефектов, нарушающих DoD. Косметический необязательный backlog допустим, если он явно описан и не мешает сценарию.
7. Регрессия ранее принятого критерия снимает его PASS. Текущий спринт блокируется до исправления и повторной проверки зависимого сценария. Старый отчёт сохраняется как история.
8. Mock-тесты подтверждают контракты, но не заменяют реальные Auth/Storage/AI и проверку выбранного сдаваемого окружения.

- Зафиксировать политику старого `sq_state_v1`: безопасный экспорт и сохранение оригинала; при необходимости переноса реализовать валидируемый импорт в спринте 2. Не обещать существующий автоматический импорт.

DoD:
- **0.1** Чистый запуск по инструкции воспроизводим; check/build и существующий regression suite проходят, исходные 178 assertions сохранены.
- **0.2** Все семь маршрутов открываются напрямую; нет потери обязательных экранов и seed, неизвестные данные не выдуманы.
- **0.3** Есть актуальная матрица «требование → реализация → проверка → спринт», включая все A01–A19 и ограничения миграции.
- **0.4** Нет блокера запуска, повреждения данных или нарушения паритета миграции. Известные функциональные пробелы назначены спринтам 1–6 и не объявлены исправленными.
- **0.5** Отчёт приёмки фиксирует фактическую версию, результаты и воспроизводимые команды.

## Спринт 1. R1, правовые инварианты и скоринг

Цель: неподкреплённое решение не может повысить риск ни через UI, ни через прямую серверную команду.

Работы:
- Согласовать единую таблицу допустимых статусов и переходов R1–R6. Проверить клиентскую и серверную реализации одинаковыми сценариями.
- Для R1 различать неизвестное основание и проверенное отсутствие; проверять источник, дату и соответствие объекту. Изменение основания снимает устаревшее подтверждение.
- Для R2 требовать непустую дословную цитату и связь с исходным материалом во всех путях подтверждения, включая ручной factor command.
- Для R5 проверять оба значения готовности, источники, даты и порог; пересмотр наблюдений требует нового решения. Направление разрыва сверить с исходным ТЗ, не принимать `Math.abs` за доказанное требование.
- Проверить уникальность кодов, веса, cap и границы зон; отклонение/отзыв убирает баллы.

DoD:
- **1.1** Unknown, недоступный реестр и действующее проверенное основание не дают подтвердить R1 без новой документированной проверки отсутствия.
- **1.2** R2 нельзя подтвердить с пустой/выдуманной цитатой или без исходного материала через любой публичный путь записи.
- **1.3** R5 проходит проверки 19/20/21 п.п., неизвестных значений, обоих направлений разрыва по ТЗ и пересмотра наблюдения.
- **1.4** Веса 35/25/10/15/10/5; максимум 100; красная зона только при score ≥60 и подтверждённых R1+R2. Контрольные A/B/C: 35 yellow / 70 red / 10 green. Дубликаты и гипотезы не добавляют баллы.
- **1.5** Отрицательные проверки UI/domain/server проходят; недопустимая команда не меняет состояние частично. Термины интерфейса не объявляют признак риска установленным правонарушением.

## Спринт 2. Доказательства, история и сохранение

Цель: каждое решение можно восстановить и объяснить после перезапуска.

Работы:
- Закрепить контракты evidence, decision, analysis run и signal version; стабильные ID, ссылки, происхождение, дата фиксации, автор решения, версия исходных фактов.
- Сохранять подтверждение, отклонение и пересмотр с причиной и предыдущим/новым состоянием; историю нельзя перезаписывать клиентом.
- Проверить атомарность публикации/доказательства/решения, конфликт версий двух вкладок и защиту от повторного сохранения.
- Проверить файлы, reload, ошибки загрузки/метаданных, восстановление и изоляцию пользователей. Сохранить текущую архитектуру workspace, если она удовлетворяет контрактам; нормализация сама по себе не цель.
- Реализовать безопасный экспорт/восстановление состояния и согласованную в спринте 0 политику старых данных. Повреждённые/неизвестные версии не должны молча затираться seed.

DoD:
- **2.1** После reload/повторного входа доступны исходный текст, файлы, решения, отказы и журнал; файл всегда соответствует своему ID и подписи.
- **2.2** Для каждого изменения видны автор, время, причина и изменённые данные; прежнее решение сохраняется. Автор в подключённом режиме определяется серверной аутентификацией.
- **2.3** Конкурентная устаревшая запись отклоняется; повтор команды не создаёт второго решения; сбой не оставляет частично принятую операцию или потерянное доказательство.
- **2.4** Два настоящих тестовых пользователя не читают и не изменяют данные/файлы друг друга; анонимный доступ закрыт. Проверены истечение подписанной ссылки и повторное получение своей ссылки.
- **2.5** Восстановление тестового экспорта сверено по содержимому и связям. Оригинал старых данных сохранён; политика совместимости отражена в UI/README и проверена.

## Спринт 3. Мониторинг рекламы и извлечение доказательств

Цель: ручной ввод и CSV дают корректные, прослеживаемые публикации и цитаты.

Работы:
- Проверить RU/KZ, область отрицаний, суммы/телефоны/каналы и единую семантику локального извлечения.
- Разделить дословную цитату для хранения и сокращённый текст для показа. Проверить диапазоны цитат на Unicode, переносах строк и длинных предложениях.
- Проверить определение площадки по hostname, допустимые URL, даты публикации/фиксации, дедупликацию и связь с объектом.
- CSV: кавычки, multiline, разделители, пустые/битые строки, предпросмотр, ошибки по строкам и явное подтверждение привязки к ЖК. Неоднозначное имя не привязывать автоматически.

DoD:
- **3.1** Фиксированный RU/KZ regression corpus проходит; «без комиссии»/«не упустите» не скрывают депозит, «без предоплаты» само по себе не создаёт R2.
- **3.2** Каждая сохранённая цитата — точная непустая подстрока неизменного исходного текста; длинная цитата не заменена многоточием.
- **3.3** CSV сохраняет только явно выбранные валидные строки и их привязки; ошибки видны; повторный импорт не создаёт дубликатов.
- **3.4** Поддельный домен/путь не распознаётся как известная площадка; опасные протоколы отвергаются. Новые публикации сохраняют источник и время фиксации, неизвестная дата публикации отмечена честно.
- **3.5** E2E «ввод/CSV → предпросмотр → сохранение → объект → reload» проходит, с сохранением инвариантов спринтов 1–2.

## Спринт 4. Настоящий AI с подтверждением аналитиком

Цель: реальная модель помогает анализу, но не принимает решение о риске.

Работы:
- Проверить серверный адаптер, строгую схему ответа и допустимые факторы, валидацию цитат, лимиты/таймауты и недоверие к инструкциям внутри рекламы.
- Хранить ID запуска, модель/провайдера, версию prompt/schema, снимок входа, время, результат/ошибку и последующее решение. При необходимости конфиденциальные служебные данные хранить отдельно от UI.
- Привязать результат к неизменному вводу: смена объекта/текста/маршрута не позволяет сохранить устаревший ответ.
- Подготовить фиксированный eval-набор: RU/KZ, положительные/отрицательные случаи, смешанные отрицания, длинный текст и prompt injection. До прогона закрепить ожидаемые решения.
- Выполнить реальный inference через Edge и браузер, а не только mock. Проверить явную ошибку провайдера без скрытой подмены локальным парсером.

DoD:
- **4.1** Новый текст проходит настоящий provider → Edge → UI; отчёт содержит воспроизводимые обезличенные входы, модель, время и результаты.
- **4.2** Все обязательные eval-кейсы проходят ожидаемые проверки; произвольные/пустые цитаты и неверные типы отвергаются. Это не заявление о точности на любых данных.
- **4.3** До решения аналитика гипотезы дают 0 баллов. Подтверждение и отказ вместе с исходником переживают reload; повторный клик не дублирует решение.
- **4.4** Проверены timeout, 429, неверный JSON, смена маршрута/ввода и встроенные инструкции. Ошибка не выглядит как успешный AI-анализ.
- **4.5** Секрет отсутствует в клиентском bundle, browser storage и Git; запросы требуют аутентификации и соблюдают квоты. Нет доступного провайдера — BLOCKED, а не PASS по mocks.

## Спринт 5. Сигнальные карточки, экспорт и полный цикл

Цель: получить самостоятельную проверяемую карточку по зафиксированной версии расследования.

Работы:
- Оформить переходы draft → confirmed/returned → новое решение, с автором, временем и причиной.
- Сохранять полный снимок принятой версии: объект, факторы, score, источники, цитаты, сведения о файлах и решении. Снимок не должен зависеть от текущего изменяемого списка публикаций.
- При новых фактах требовать пересмотра, сохранять прежнюю принятую версию доступной.
- Довести печать/PDF: ID и версия, статус, даты, автор, источники/URL, цитаты, происхождение данных, ограничения и пояснение характера риска. Общий JSON-экспорт не заменяет сигнальную карточку.

DoD:
- **5.1** E2E «новая публикация → AI → подтверждение/отказ → score → сигнал → экспорт» проходит на настоящем подключённом режиме; отказ не добавляет баллов.
- **5.2** Изменение влияющих фактов снимает актуальность подтверждения; старая версия остаётся неизменной и доступной, новая требует решения.
- **5.3** Полученный многостраничный PDF реально открыт и просмотрен: кириллица, длинные цитаты, переносы, источники и даты читаются, ничего не обрезано.
- **5.4** Score/факторы/источники экспорта совпадают со снимком выбранной версии; черновик и возвращённый сигнал явно обозначены.
- **5.5** Сценарий проходит после reload, по прямой ссылке и на мобильном viewport; пустые/отсутствующие данные не заменяются вымышленными.

## Порядок работы внутри спринта

Проверка входного gate → воспроизведение пробелов → реализация минимально необходимых исправлений → соответствующие негативные и позитивные проверки → накопленная регрессия → запись свидетельств → PASS или продолжение этого же спринта.

Сроки и размер задач уточняются после спринта 0: нынешняя реализация уже покрывает часть работ, но свежих результатов приёмки нет. Дедлайн не даёт права пропустить DoD. При нехватке времени сокращаются дополнительные функции, а не требования достоверности, сохранности и проверяемости MVP.
