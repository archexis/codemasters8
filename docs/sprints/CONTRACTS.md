# Зафиксированные контракты v2

Это целевое поведение. Поля ниже пока не означают существующий API. Вводить их по указанным спринтам, одновременно в TS, SQL, UI и фикстурах.

## C1. Базовые решения и доказательства — S1

Сохранить `FactorStatus` и веса. Добавить runtime-схемы команд в `src/lib/validation.ts`, типы в types.ts. Reject неизвестных code/status/type, неверных дат, NaN/Infinity, пустых обязательных полей и неоднозначных ID. SQL повторяет проверки: TypeScript — не граница доверия.

Минимальный `Evidence` расширяет текущий объект, не вводит отдельную таблицу:

```ts
type Evidence = {
  id: string; zkId: string;
  kind: 'publication' | 'legal-review' | 'observation' | 'document';
  source: string; date: string; // реальная календарная YYYY-MM-DD
  adId?: string; quote?: string;
  text?: string; // зафиксированное содержание акта/документа/сверки
  mediaIds?: string[]; // добавляются в S2; не требуются для текстового доказательства
};
```

Источник — проверяемая ссылка ИЛИ идентификатор/название документа с сохранённым содержанием. Одна строка «проверено» без материала недостаточна. Для ручного материала дата — дата материала/проверки, не автоматически дата клика. `reviewer/at` решения назначает сервер, отдельно от evidence.date. Для DEMO автор явно демонстрационный.

| Фактор | Что обязательно для confirmed | Что не доказывает фактор |
|---|---|---|
| R1 | legalBasis `type=absent,status=absent-verified`, source, checkedAt, сохранённое описание области сверки и её результата; evidence legal-review того же объекта | unknown, недоступность реестра, отсутствие только разрешения МИО при действующей гарантии |
| R2 | evidence publication; ad существует в том же ЖК; непустая точная quote из ad.text; аналитик подтверждает предложение оплаты | выдуманная quote, чужой adId, упоминание мессенджера само по себе |
| R3 | публикация того же ЖК + quote + источник/дата подтверждения, что на дату публикации объект не введён | одна текущая произвольная строка stage |
| R4 | document evidence с сохранённым текстом обращения или файлом; дата, источник, привязка к ЖК; аналитик указывает, что обращение коллективное и о привлечении средств | generic source, несвязанная жалоба |
| R5 | два observation record: claimed и confirmed, value 0..100, source/date каждого; `abs(claimed-confirmed)>=20`; отдельное решение | одно число, одно происхождение на два числа, неизвестное значение |
| R6 | документ/текст: заявленный срок либо период простоя, наблюдаемый факт, даты/источники; обоснование значимости аналитиком | автоматический порог «N дней», отсутствующий в ТЗ |

Для R3 добавить в evidence структурированное `beforeCommissioning: { source, date, text }`; для R4 `collectiveAppeal: { concernsFundraising: true }` и текст/файл; для R6 `scheduleDeviation: { plannedDate?: string, observedDate: string, idleSince?: string, explanation: string }`, минимум plannedDate или idleSince. Boolean — заявление аналитика, а не автоматическая проверка истинности. UI обозначает это. SQL требует структурные поля и материал.

`legalBasis` получает `reviewText` и согласованные пары: unknown/unknown; absent/absent-verified; guarantee/verified; mio-permit/verified. Это варианты продукта, не исчерпывающая юридическая классификация. Если иной вариант нужен — отдельное уточнение, не подмена. Смена type/status/source/checkedAt/reviewText отзывает старый confirmed R1 даже при том же status.

Готовность: добавить `readinessClaimedSource: {value,source,date}`; observation command продолжает создавать подтверждённое наблюдение. При изменении любого из этих материалов старое решение R5 → needs-verification; при новом gap>=20 допустима новая hypothesis, баллы 0 до нового подтверждения.

Для всех confirmed/rejected/needs-verification ручных решений нужен осмысленный непустой comment. Гипотезы модели не становятся confirmed автоматически. Все шесть факторов проверяются через UI и прямой RPC. Невалидная команда не изменяет data/version/audit.

## C2. Версии, история, повтор — S2

- `AppState.schemaVersion=3`; отсутствующая версия — legacy v2; исходный sq_state_v1 — отдельный старый формат.
- Дополнить AppState `signalVersions`, существующие audit остаются доступными. Нормализованные приложения/организации вне scope.
- `AuditEvent`: id, commandId, zkId, actorId/reviewer, at, action, comment, before, after, evidence snapshot. Хранить достаточное содержание конкретного изменения, не всю копию workspace на каждое событие.
- Случайные UUID создаются один раз на намерение пользователя; retry использует тот же ID. Объект/публикация/файл не получает новый ID при сетевом повторе.
- RPC `apply_command(command,expected_version,command_id)` — единственная пишущая сигнатура; старая удаляется (DROP) в миграции, две доступные write-версии запрещены. Не оставлять две доступные write-версии.
- Для квитанций создать одну служебную таблицу `command_receipts(owner_id,command_id,payload,result_version)`, PK(owner_id,command_id), без прямого клиентского DML, с RLS. Payload сравнивать каноническим JSONB, не сырым JSON с порядком ключей.
- Порядок в транзакции: auth → lock workspace → lookup receipt → при том же payload вернуть **текущее** workspace/version и original result_version без мутации; иной payload с тем же ID → COMMAND_ID_REUSED; если receipt нет → expected_version → validate/apply/audit/receipt атомарно.
- Проверка receipt предшествует stale check: потерянный ответ должен повторяться успешно, даже если версия уже выросла. Ответ содержит replayed и appliedVersion; UI показывает актуальное состояние.
- DEMO envelope хранит state/version/receipts одним значением localStorage; чтение и запись сериализовать между вкладками Web Locks. Если API недоступен — чтение/экспорт остаются, запись блокируется объяснением, не обещать защиту на одном storage event.
- Регистрации нет: без сессии клиент работает в DEMO-конверте по умолчанию (сырое v3-состояние мигрирует и сохраняется в рабочий ключ при загрузке); сервер анонимов отклоняет через RLS/политики. Вход — только по выданной оператору учётной записи (временные аккаунты connected-режима).
- pending command хранить до отправки, удалять после ACK; после reload разрешать проверку/повтор того же ID. Не повторять автоматически изменённый payload или чужую сессию.
- repository sessionGeneration повышается при logout/user change; поздние ответы старого пользователя не могут заменить новый workspace. Очередь команд сериализована внутри вкладки.

## C3. Файлы и атомарность — S2

Нельзя сделать общую DB+Storage транзакцию. Использовать upload → одна DB-команда с ad/evidence/media/decision → cleanup только при известном откате.

Стабильный путь `<owner>/<zk>/<mediaId>.<ext>`, приватный bucket. Media: id, zkId, path, name, kind, bytes, sha256, capturedAt, note. Хеш подтверждает целостность байтов, не юридическую подлинность. PDF/изображение без OCR допускает ручную расшифровку, обозначенную как ручная.

При upload fail нет принятого решения. При достоверном RPC reject удалить только staged-файлы этого commandId; если cleanup не удался, записать retry. При timeout исход RPC неизвестен: **не удалять файл**; повторить commandId/получить receipt, затем решить cleanup. Файл, на который ссылаются evidence или signal snapshot, не должен удаляться обычным пользователем; заменить широкую Storage DELETE policy проверкой ссылок, проверить это прямым вызовом SDK. Отложенная очистка работает только со своими неподключёнными staged-файлами.

MVP restore: полный пакет JSON + файлы + manifest с размерами/хешами. Обычный `/api/export` JSON назвать экспортом данных, он не полный backup. Восстановление в пустое отдельное workspace, переназначая owner-prefix путей, сохраняя IDs/связи и исходную атрибуцию как provenance. Не выдавать импортированные решения за новые серверные действия старого автора. В непустое workspace — отказ, никакого автоматического merge.

Импортируемый архив недоверенный: SQL повторно проверяет schema/IDs/ссылки/все C1 поля. Исторические решения сохраняются с origin=imported и не считаются серверно заверенной историей этой учётной записи. Все активные confirmed факторы переводятся в needs-verification, текущие сигналы — draft до повторного решения импортирующего аналитика. Это документированное отличие восстановления через пользовательский импорт от административного восстановления всей БД. Roundtrip сравнивает тексты, источники, IDs, связи и байты с учётом именно этой таблицы преобразований; нельзя заявлять полную побитовую идентичность workspace. Receipts/квоты/авторизацию из архива не импортировать.

## C4. Публикации и дедуп — S3

`Ad.date: string|null`; неизвестная дата — null, UI «не указана»; captureAt всегда время фиксации. Нельзя считать captureAt датой публикации. Для R3 с неизвестной датой публикации нужен датированный материал, позволяющий установить рекламу до ввода, иначе confirmation блокируется.

Дедуп в пределах одного ЖК: `zkId + canonicalText`; canonicalText = полный текст, нормализованные телефоны (8XXXXXXXXXX → +7XXXXXXXXXX), пробелы/регистр. Одинаковый текст в другом ЖК допустим; это не подтверждение связи. Разные источники одинакового текста в том же ЖК показывать как возможный повтор, MVP не создаёт второй ad; можно открыть существующий. Каждая публикация хранит `sightings[]` (фиксации источника: source/date-nullable/captureAt): повтор того же текста в том же ЖК — новая фиксация у существующего ad (undated + датированная сосуществуют, вторая дата/источник не теряется). SQL пересчитывает ключ, не доверяет присланному клиентом.

CSV импорт построчный: preview → выбрать одну валидную строку → явно сопоставить ЖК → анализ/сохранение → отметить строку сохранённой. Массовый auto-confirm не нужен. Каждая строка имеет rowId/номер, errors, mappedZkId|null, savedAdId|null. Неоднозначный/неизвестный hint = null, предыдущий selection не наследуется.

Оригинальный текст неизменен. Quote должна быть точной подстрокой. Для parser span — UTF-16 индексы JS, `text.slice(start,end)` проверяется; нормализация не меняет сохранённый оригинал. Отображаемая сокращённая цитата не сохраняется вместо полной.

## C5. AI — S4

Для MVP внешний AI извлекает **R2 и R3** из рекламы. R1/R4/R5/R6 требуют других материалов и остаются ручными. Не извлекать отсутствие основания из рекламного заявления. Это намеренное сужение нынешнего prompt, сохраняющее содержательный AI-поток.

`analysis_runs` — отдельная таблица для доверенного результата Edge: id, owner_id, zk_id, input_snapshot(text + metadata), input_hash, provider/model, prompt_version, schema_version, status(pending/succeeded/failed), hypotheses[{id,code,quote,reason}], started_at, finished_at, error_code. Клиент имеет только own SELECT; INSERT/UPDATE только серверным Edge-клиентом с серверным секретом после проверки пользовательского JWT. Секрет не передаётся в браузер, не используется в обычном repository/API. Не включать role key в отчёты. Это новая серверная конфигурационная зависимость S4, не существующий факт.

Edge получает runId/zkId/полный snapshot; проверяет принадлежность ЖК. Уникальный (owner_id,id) и атомарный insert pending определяют единственного исполнителя вызова. Повтор того же runId/input не вызывает LLM второй раз: возвращает сохранённый результат либо pending. Иной input с прежним ID → 409. Не маскировать сбой БД под quota 429. Если клиент может передать ID другого владельца, не раскрывать существование чужой строки или её результат.

Команда решения ссылается на runId/hypothesisId/adId; SQL проверяет ownership, успешный run, совпадение input и цитаты. hypothesisId без runId отвергается (сиротские ссылки срезаются при миграции с пометкой, runId не выдумывается). Реальный AI provenance берётся из серверного run, а не из клиентского `realAI:true`. DEMO хранит результат локально с явным origin=local-parser.

Публикация сохраняется один раз, каждую гипотезу можно независимо подтвердить/отклонить/оставить на проверку. После reload решения видны. Комментарий аналитика отделён от reason модели. R3 всё равно требует C1; наличие AI quote само по себе недостаточно.

## C6. Сигналы — схема S2, поток S5

`SignalVersion`: id, zkId, revision, status, at, reviewer, comment, sourceVersion, snapshot. Snapshot включает Complex, подтверждённые factors/evidence, связанные ads/media manifests, score/zone/weightsVersion, AI provenance только для использованных решений. Не сохранять signed URL как постоянную ссылку; хранить mediaId/path/hash и получать временную ссылку при чтении.

`signals[zkId]` — текущий draft/указатель на последнее решение; `signalVersions` — append-only записи. Подтверждение и возврат добавляют версии. Новые факты открывают draft с basedOnRevision и reason, а не меняют прошлую confirmed-версию. Повтор решения с тем же commandId не создаёт новую revision.

До S5 допускается чтение старого signal UI через адаптер. Нельзя задним числом реконструировать отсутствующий исторический снимок из текущих ads: пометить legacyIncomplete и требовать новой проверки перед полноценным экспортом. Ранние решения без снимка хранятся как revision с legacyIncomplete:true без snapshot (id `legacy-<zk>-r1`, повтор — no-op). Повтор решения с тем же commandId — replay квитанции без новой revision (TS и SQL).

Политика invalidation MVP консервативна: любое изменение фактов/доказательств объекта → новый draft. Простой просмотр/экспорт/попытка отклонённой команды и запись AI run сами по себе сигнал не инвалидируют. Score вычисляется из принятого snapshot, header и тело используют одну версию.
