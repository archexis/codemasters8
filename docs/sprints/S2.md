# S2 — сохранность, история, файлы и восстановление

Вход: S1 PASS. Реализовать C2/C3 и схему C6. Порядок S2.1 → S2.6. Не реализовывать AI pipeline раньше S4.

## S2.1 — schemaVersion и загрузка

Файлы: types.ts, validation.ts, создать state-migrations.ts, repository loadState, SQL migration; `tests/unit/state-migration.test.ts`.

Схема v3, строгая проверка вложенных сущностей и ссылок. Известный v2 → миграция; неизвестная future version → понятный отказ от записи + экспорт исходного файла. Повреждённые данные не заменять initialState. Legacy sq_state_v1: отдельная команда импорта из файла с preview; raw backup остаётся нетронутым. Несуществующие старые бинарные файлы помечать missing, не заявлять восстановление.

Тесты: валидный v2; битый JSON; отсутствующий adId/mediaId; будущая версия; неизвестный status; повтор миграции; v1 с metadata без bytes. Ожидание: исправимые legacy сведения перенесены с provenance, неподкреплённые confirmed сняты, исходник сохранён, повтор не меняет результат.

## S2.2 — command receipts, конфликты, сессия

Файлы: domain command envelope, repository, App commit/auth callbacks, SQL RPC/receipts, cloud tests; `tests/unit/idempotency.test.ts`.

Реализовать порядок C2 и убрать доступ к старой write RPC сигнатуре. Сериализовать очередь одной вкладки. Добавить явное восстановление после STALE_VERSION: перечитать состояние, сохранить пользовательский draft, показать конфликт; не применять решение к новым фактам автоматически. Смена пользователя отменяет/игнорирует старые ответы.

Тесты: одинаковые commandId/payload дважды → один audit/одно изменение version; тот же ID с другим payload → отказ; network lost после COMMIT → retry успешен без дубля; две команды разных вкладок с одной expected_version → одна принята, вторая stale; после reread требует нового решения; logout A/login B, поздний ответ A → UI остаётся B. DEMO: две реальные browser pages и Web Locks, не только mock.

## S2.3 — публикация с вложением как единое решение

Файлы: Analyze save, Detail upload, repository upload/remove, types, SQL atomic ad bundle, storage policies; `tests/e2e/evidence-failures.spec.ts`.

Файлы загружаются до финального DB commit; одна команда принимает publication/evidence/media/решение. saved=true только после ACK. Реализовать C3, включая неизвестный результат timeout. Нельзя просто всегда удалять файл в catch. При retry использовать прежние mediaId/path/commandId. У metadata проверить ownership/zkId/existence, размер/тип по Storage metadata; не доверять клиентскому path.

Обязательные fault cases: upload fail; RPC validation fail; RPC commit и потеря ответа; cleanup fail; повтор после reload; неверный owner prefix; чужой или missing Storage object. Проверить data/audit/receipt и наличие байтов после каждого исхода.

## S2.4 — неизменная история и подготовка сигнала

Файлы: types, domain, SQL, Detail History; создать `src/lib/signal-snapshot.ts`; unit history tests.

Audit before/after/evidence snapshot и server actor/time. Реализовать append-only SignalVersion C6 при существующих confirm/return командах; пока Detail использует адаптер последней версии. Legacy signal без полного снимка → legacyIncomplete, не «восстановить» прошлое сегодняшними данными.

Тест: подтвердить фактор → отклонить → повторно подтвердить → три события, причины/материалы доступны; confirm signal → изменить объект → новая draft, первый snapshot deepEqual первоначальному; второй confirm → revision+1. Прямой клиент не может UPDATE/DELETE audit/version через workspace или обходную RPC.

## S2.5 — полный backup и restore

Файлы: создать backup.ts, UI App, серверный restore RPC, backend export labels; tests backup.

Формат: ZIP с `manifest.json`, `workspace.json`, `files/<mediaId>.<ext>`. При необходимости выбрать и зафиксировать одну ZIP dependency в lockfile. Manifest version, IDs, bytes/sha256 и source schema; никакого `../`/absolute archive path. Ограничить суммарный распакованный размер до 200 МБ и число файлов до 100 для MVP; отказ до записи при превышении. Данные/файлы пользователя не отправлять внешнему сервису упаковки.

Restore: validate весь пакет и ссылки → пустое target workspace → staged upload с новым owner-prefix → единая DB запись/import event → ACK/cleanup по C3. Auth/ownership и системный reviewer не импортируются как авторизация. Активные confirmed → needs-verification, signals → draft; история помечается imported. Предпросмотр заранее показывает эти преобразования. SQL валидирует пакет, не доверяет проверке ZIP в браузере. Непустой target → отказ. Если файл отсутствует или hash неверен, обычный полный restore блокируется с перечнем; legacy import отдельно допускает missing mark без ложного полного восстановления.

## S2.6 — настоящая изоляция и долговечность

Файлы: tests/live, tools/local-smoke, Storage policies, MediaCard.

Два временных пользователя: B не читает workspace/media A и не получает подписанную ссылку A; anonymous denied; expired URL перестаёт отдавать файл, новая own URL работает. Для теста TTL использовать короткий срок через SDK и измеряемое истечение, не ждать 5 минут. A не удаляет файл, используемый принятым evidence/snapshot; unused staged file удалить может. Ошибка превью показывает missing/retry, а не чужую картинку.

Backup A → restore в отдельное чистое пространство → сравнить данные, связи и SHA256 байтов после login/reload с учётом documented status/provenance преобразования C3. Поддельный confirmed из произвольного архива не начисляет баллы. Проверить DEMO IndexedDB отдельно.
